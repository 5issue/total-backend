### [단계 1] 장바구니 → 주문서 생성

---

- code
    
    ```mermaid
    sequenceDiagram
        autonumber
        actor Client as FE (Client)
        participant Order as 주문 서비스 (Order)
        participant Product as 상품 서비스 (Product)
        participant Redis as Product Redis (선점 저장소)
    
        Client->>Order: POST /api/v1/orders/checkout (주문서 진입)
        activate Order
    
        opt 기존 활성 주문서 존재 시 만료 처리
            Order->>Order: 기존 주문서 EXPIRED 상태 변경
            Order->>Product: POST /internal/v1/products/inventory/release (동기 재고 복구)
        end
    
        Order->>Order: 신규 Order 엔티티 생성 (status: CHECKOUT_CREATED, 자체 TTL 15분 설정)
        Order->>Product: POST /internal/v1/products/inventory/hold (동기 선점 요청)
        activate Product
        Product->>Redis: 선점 데이터 저장 (No-TTL, 수량 Redis 저장)
        activate Redis
        Redis-->>Product: 선점 완료
        deactivate Redis
        Product-->>Order: 200 OK (선점 성공)
        deactivate Product
    
        Order-->>Client: 200 OK (주문서 렌더링 데이터 및 orderId 반환)
        deactivate Order
    ```
    

**Rollback범위: REST 동기 통신 범위 → task 2~9(9 시점에서 커밋 수행)**

### [단계 2] 주문서 → 결제창 진입 및 사전 동기 검증

---

- code
    
    ```mermaid
    sequenceDiagram
        autonumber
        actor Client as FE (Client)
        participant Order as 주문 서비스 (Order)
        participant Payment as 결제 서비스 (Payment)
    
        Client->>Order: POST /api/v1/orders/place-order
        activate Order
        Order->>Order: 15분 TTL 폐기 & 상태 PAYMENT_PENDING 변경<br/>(결제 하드 타임아웃 5분 데드라인 설정)
        Order-->>Client: 200 OK
        deactivate Order
    
        Client->>Payment: POST /api/v1/payments/checkout (orderId, amount)
        activate Payment
        Payment->>Order: GET /internal/v1/orders/{orderId} (동기 조회)
        activate Order
        Order-->>Payment: 금액, 소유자 ID, 상태(PAYMENT_PENDING), 남은 타임아웃 반환
        deactivate Order
    
        Payment->>Payment: 금액 위변조 및 주문 소유권 검증
    
        alt 유효시간 만료 또는 검증 실패
            Payment-->>Client: 400 Bad Request (결제창 오픈 차단)
        end
        deactivate Payment
    ```
    


**Rollback범위**

- **주문: task 2~3**
- **결제: task 5~9 (commit 없음. 금액, 소유권 검증 실패 시 400 Bad Request 응답)**

### [단계 3] PG 결제 승인 및 비동기 후속 처리

---

- code
    
    ```mermaid
    sequenceDiagram
        autonumber
        actor Client as FE (Client)
        participant Payment as 결제 서비스 (Payment)
        participant Toss as 토스페이먼츠 (PG)
        participant Order as 주문 서비스 (Order)
        participant OrderMQ as RabbitMQ (order.topic.exchange)
        participant Product as 상품 서비스 (Product)
    
        activate Payment
    
        %% 1. 바로 토스 승인 호출 (사전 잠금 API 제거)
        Payment->>Toss: 외부 토스 결제 승인 API 호출 (토스 결제 승인)
        activate Toss
        Toss-->>Payment: 200 OK (카드 결제 완료)
        deactivate Toss
    
        Payment->>Payment: 결제 상태 SUCCESS 기록
    
        %% 2. 결제 완료를 Order에 단 1번 동기 통보 (조건부 상태 전이)
        Payment->>Order: POST /internal/v1/orders/{orderId}/complete-pay (동기 호출)
        activate Order
    
        alt 정상: 5분 이내 결제 성공 (UPDATE ... WHERE status = 'PAYMENT_PENDING' 성공)
            Order->>Order: 상태를 PAID로 변경
            Order->>OrderMQ: 발행: order.inventory.confirm (재고 확정 이벤트)
            Order-->>Payment: 200 OK
            Payment-->>Client: 200 OK (결제 완료 화면)
        else 예외: 5분 초과로 이미 만료 배치에 의해 EXPIRED된 경우
            Order-->>Payment: 409 Conflict (주문 만료 에러 반환)
            deactivate Order
            Note over Payment, Toss: [보상 트랜잭션] 즉시 토스 취소 API 호출
            Payment->>Toss: 에러 catch 후 보상 결제 승인 취소 API 호출
            alt 정상: 결제 승인 취소 성공
    	        Payment-->>Client: 400 Bad Request ("결제 유효시간 초과로 자동 환불되었습니다")
    		      else 에러 : 결제 승인 취소 실패
    			      Payment-->>Payment: 결제 취소 이력 테이블에 실패 기록 (배치 스케줄러로 재시도)
    			      Payment-->>Client: 400 Bad Request ("결제 유효시간 초과로 주문에 실패했습니다. 결제 취소에는 수 분에서 수 일이 소요될 수 있습니다.")
    		    end
    		end
        deactivate Payment
    
        %% 3. 백그라운드 재고 확정
        OrderMQ->>Product: 메시지 비동기 소비 (order.inventory.confirm)
        activate Product
        Product->>Product: Redis 선점 Key 삭제 & RDB 재고 영구 차감
        deactivate Product
    ```
    


**Rollback범위**

- 결제: task 2~3 (아웃박스 커밋 실패 시 try-catch로 승인 취소 API 호출)

## 2. 사용자 주문 취소 (출고 지시 전)

---

- code
    
    ```mermaid
    sequenceDiagram
        autonumber
        actor Customer as 고객
        participant Order as 주문 서비스
        participant OMS as OMS
        participant Payment as 결제 서비스
        participant Toss as PG사 (Toss)
        participant MQ as Message Queue (RabbitMQ)
        participant Product as 상품 서비스
    
        Customer->>Order: 주문서 조회 및 취소/환불 요청 (마이페이지)
        activate Order
        
        Order->>OMS: GET /internal/v1/oms/orders/{orderId}/cancel-eligibility (동기)
        activate OMS
        
        alt [취소 불가] 패킹/출고 진행 중 (RELEASE_INSTRUCTED 이상)
            OMS-->>Order: 상태: ALREADY_PROCESSING (취소 불가)
            Order-->>Customer: "상품 포장/출고가 시작되어 즉시 취소가 불가합니다.<br/>1:1 고객 문의를 이용해주세요."
        else [취소 가능] 입금확인/결제완료 단계
            OMS-->>Order: 상태: CANCELLABLE
            deactivate OMS
            
            Order->>Order: DB 주문 상태 UPDATE (CANCEL_PROCESSING)
            
            Order->>Payment: POST /internal/v1/payments/{paymentId}/cancel
            activate Payment
            Payment->>Toss: PG 결제 전액 취소 요청
            activate Toss
            Toss-->>Payment: 취소 승인 완료
            deactivate Toss
            Payment->>Payment: DB 결제 상태 CANCELED 업데이트
            Payment-->>Order: 결제 취소 성공 응답 (HTTP 200)
            deactivate Payment
            
            Order->>MQ: 재고 복구 이벤트 발행 (order.canceled.inventory-restore)<br/>* Outbox 패턴 적용
            
            MQ->>Product: 메시지 소비 (product.inventory-restore.queue)
            activate Product
            Product->>Product: [멱등성 검증] event_id 기반 중복 처리 방어
            Product->>Product: [동시성 제어] Redis 분산 락 획득 후 논리 재고 원복
            Product->>MQ: 재고 복구 완료 이벤트 발행 (product.inventory.restored)
            deactivate Product
            
            MQ->>Order: 메시지 소비 (order.inventory-restored.queue)
            Order->>Order: 주문서 객체 최종 CANCELED 상태로 전이
            Order-->>Customer: 앱 푸시 / 웹소켓으로 주문 취소 및 환불 최종 완료 알림
        end
        deactivate Order
    ```
    


**Rollback 범위**

- task 2~11
- task 12 이후는 비동기 처리이므로 이전에 롤백이 일어나지 않았다면 최소 1회 실행 보장.

## 3. 출고 이후(배송 중/완료) 온도대별 반품 및 환불 흐름

---

- code
    
    ```mermaid
    sequenceDiagram
    autonumber
    actor Client as FE (고객)
    actor BO as Admin (BO 관리자)
    participant Order as 주문 서비스 (Order)
    participant MQ as RabbitMQ
    participant OMS as 주문관리 (OMS)
    participant WMS as 물류창고 (WMS)
    participant Product as 상품 서비스 (Product)
    participant Payment as 결제 서비스 (Payment)
    participant Toss as 토스페이먼츠 (PG)

    %% 1. 반품 접수 공통
    Client->>Order: POST /api/v1/orders/{orderId}/returns
    activate Order
    Order->>Order: OrderClaim 생성 (status: REQUESTED)<br/>주문 상태 변경 (RETURN_REQUESTED)
    Order-->>Client: 200 OK ("반품 신청이 완료되었습니다.")
    Order->>MQ: order.return-requested 이벤트 발행
    deactivate Order

    MQ->>OMS: 메시지 소비 (oms.return-requested.queue)
    activate OMS
    Note over OMS: OmsOrder(DELIVERED 불변 유지)<br/>신규 OmsReturn 및 OmsReturnItem 생성 (status: REQUESTED)
    deactivate OMS

    %% 2. 관리자 통합 판정 API 진입점
    Note over BO, OMS: [통합 판정 API] 품목별 decision (COLDCHAIN, LOGISTICS, REJECT)
    BO->>OMS: POST /api/v1/admin/oms/orders/{omsOrderId}/return-judgement
    activate OMS
    OMS->>OMS: OmsReturn 및 OmsReturnItem 판정 상태 업데이트

    alt [Case 1: 상온 품목(APPROVE_LOGISTICS) 포함 시]
        Note over OMS: WMS 검수 지시만 우선 발행 (환불 이벤트는 WMS 검수 후로 지연)
        OMS->>MQ: oms.return.inspection-requested 발행 (상온 품목 ID 목록)
    else [Case 2: 콜드체인(APPROVE_COLDCHAIN) 단독 승인 시]
        Note over OMS: 즉시 통합 단일 환불 지시 발행
        OMS->>MQ: oms.order-refund.requested 발행 (폐기 금액 및 품목 ID 목록)
    else [Case 3: 전 품목 REJECT 판정 시]
        Note over OMS: OmsReturn 상태 REJECTED 종결
    end
    OMS-->>BO: 200 OK (판정 결과 반환)
    deactivate OMS

    %% 후속 비동기 파이프라인 (LOGISTICS 회수, 검수 및 통합 환불)
    opt [Logistics 회수 & 검수 완료 후 통합 환불 진행]
        MQ->>WMS: 메시지 소비 (wms.return-inspection.queue)
        activate WMS
        WMS->>WMS: 실물 수거 및 입고/검수 수행
        
        opt 재판매 가능(정상 재고) 판정 시
            WMS->>MQ: wms.return-inspected (실물 입고 완료) 발행
            MQ->>Product: 메시지 소비 (product.inventory.sync)
            activate Product
            Product->>Product: 가용 재고 복구 (Redis/DB 원자적 증가)
            deactivate Product
        end

        WMS->>MQ: wms.return.inspected 발행 (검수결과, approvedItemIds[])
        deactivate WMS

        MQ->>OMS: 메시지 소비 (oms.wms-inspected.queue)
        activate OMS
        Note over OMS: [Coldchain 금액 + 검수통과 상온 금액] 합산<br/>귀책 배송비 차감 후 단 1회의 최종 환불 지시 발행
        OMS->>MQ: oms.order-refund.requested 발행 (최종 통합 환불금액)
        deactivate OMS

        MQ->>Payment: 메시지 소비 (payment.refund.queue)
        activate Payment
        Payment->>Toss: POST /v1/payments/{paymentKey}/cancel (PG 취소 1회 실행)
        activate Toss
        Toss-->>Payment: 200 OK
        deactivate Toss
        Payment->>Payment: 결제 상태 CANCELED 갱신
        Payment->>MQ: payment.canceled 이벤트 발행
        deactivate Payment

        MQ->>Order: 메시지 소비 (order.payment-canceled.queue)
        activate Order
        Order->>Order: OrderClaim(COMPLETED), Order 상태 REFUNDED 확정
        deactivate Order
    end
    ```
    


1. **Rollback 범위**
    - **Task 1~3: 반품 접수 및 주문 상태 롤백 (Client ➔ Order)**
        - **조건:** 클레임 생성 실패 시 Task 1~3 전체 롤백 (200 OK 및 이벤트 미발행).
    - **Task 9~11: [1. 상온 미포함] 자체폐기 단독 승인 및 즉시 환불 롤백 (BO ➔ OMS)**
        - **조건:** 상온 품목에 폐기 승인 시도(`OMS_CONFLICT_TEMPERATURE`), DB 커밋 에러, Outbox 적재 실패 시 Task 9~11 전체 롤백.
    - **Task 14~16: [1. 상온 미포함] PG 결제 취소 요청 및 결제 취소 상태 롤백 (Payment ➔ Toss)**
        - **조건:** PG사 통신 장애, 타임아웃, 결제 원장 DB 갱신 실패 시 Task 14~16 롤백 (보상 재시도 스케줄러 이관).
    - **Task 23~25: [2. 상온 포함] 역물류 회수 지시 접수 롤백 (BO ➔ OMS)**
        - **조건:** OMS 반품 상태 전이 실패 또는 DB 커밋 에러 발생 시 Task 23~25 전체 롤백.
    - **Task 33~34: [2. 상온 포함] WMS 실물 수거 및 입고 검수 처리 롤백 (WMS)**
        - **조건:** WMS 내부 수거/검수 처리 중 데이터 오류 발생 시 Task 33~34 롤백.
    - **Task 35~36: [2. 상온 포함] WMS 검수 수신 및 통합 환불금 산정 롤백 (WMS ➔ OMS)**
        - **조건:** 상태 미일치(`OMS_INVALID_STATUS`) 또는 통합 환불 산정/DB 갱신 실패 시 Task 35~36 전체 롤백.
    - **Task 39~41: [2. 상온 포함] PG 결제 취소 요청 및 결제 취소 상태 롤백 (Payment ➔ Toss)**
        - **조건:** PG사 승인 취소 오류 또는 Payment DB 갱신 실패 시 Task 39~41 롤백.
2. **통합 환불 프로세스 (단일 이벤트 발행)**

   > 전체환불 정책에 따라 하나의 주문에 대해 PG 취소를 1회만 호출하도록, 상온 품목 수거 검수 완료 시점까지 이벤트를 지연·통합합니다.
   
    1. **상온/비식품이 포함된 경우 (`APPROVE_LOGISTICS` 존재)**
        - **Client(Admin) ➔ OMS (API):** `Approve_Logistics` 확인.
        - **OMS ➔ WMS (MQ):** 상온 물품만 검수 요청 (`oms.return.inspection-requested`). *(※ 이때 승인된 냉동/냉장 품목은 `APPROVE_COLDCHAIN` 상태만 기록하고 환불 이벤트 발행은 대기)*
        - **WMS ➔ OMS (MQ):** 검수 완료 (`wms.return.inspected`). 기존 승인된 냉동/냉장 가액 + 검수 통과된 상온 가액을 합산하고 배송비 차감(고객 귀책 시 3,000원) 후 **통합 환불 이벤트 1회 발행**.
        - **OMS ➔ Payment (MQ):** `oms.order-refund.requested` 이벤트 소비 및 PG 결제 취소 실행.
    2. **주문에 상온/비식품이 없는 경우 (냉동/냉장만 존재)**
        - **Client(Admin) ➔ OMS (API):** WMS 검수가 불필요하므로 즉시 냉동/냉장 환불금 산정 후 **곧바로 환불 이벤트 1회 발행 및 응답**.
        - **OMS ➔ Payment (MQ):** `oms.order-refund.requested` 이벤트 소비 및 PG 결제 취소 진행.
