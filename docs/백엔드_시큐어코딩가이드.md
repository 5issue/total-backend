# 1. 목적

백엔드팀이 Java 및 Spring Boot 기반 API와 서버 로직을 개발·변경할 때 발생할 수 있는 주요 보안 취약점을 예방하기 위한 기본 시큐어 코딩 지침을 전달한다.

본 문서는 「2026 주요정보통신기반시설 기술적 취약점 분석·평가방법 상세가이드」의 Web Application 취약점 항목을 백엔드 개발 관점에서 재구성하였으며, 취약점 점검 절차보다는 **코드 작성 시 지켜야 할 기본 보안 원칙과 취약한 구현 방식의 방지**에 초점을 둔다.

# 2. 적용 범위 및 전제

## 프로젝트 백엔드 구성

현재 백엔드팀 자료에서 확인된 기술 구성은 다음과 같다.

| 구분 | 기술 |
| --- | --- |
| Language | Java 25 |
| Framework | Spring Boot 4.1.0 |
| DBMS | MySQL, PostgreSQL |
| Message Broker | RabbitMQ |
| Outbox | Spring Application Level |
| Caching Layer | Redis |
| Container / Infra | Docker, Kubernetes |

현재 확인된 서비스는 회원(member), 주문(order), 결제(payment), 상품(product), OMS, WMS, SCM이다.

본 가이드는 위 환경에서 개발되는 **백엔드 API 및 서버 애플리케이션 코드**에 적용한다.

파일 업로드·다운로드, 사용자 입력 기반 외부 URL 요청 등 특정 기능과 관련된 기준은 해당 기능을 구현하는 경우 적용한다.

DB 접근 기술이나 인증 구현 방식에 관계없이 적용할 수 있는 기본 보안 원칙을 정의하며, 아래 코드 예시는 특정 라이브러리나 구현 기술을 강제하기 위한 것이 아니라 보안 원칙을 설명하기 위한 예시이다.

# A. 공통 원칙

| 항목ID | 요구사항 | 조치 방법 | 근거 |
| --- | --- | --- | --- |
| BE-01 | 외부 입력값 서버 검증 | 클라이언트에서 전달되는 값을 용도에 맞게 서버에서 검증 | CI, SI 등 |
| BE-02 | 중요 업무 값 서버 검증 | 가격·수량·업무 상태 등 중요 값을 클라이언트 값만으로 결정하지 않음 | PV, IN |

## BE-01. 외부 입력값 서버 검증

클라이언트에서 전달되는 값은 사용자가 임의로 변경할 수 있으므로 프론트엔드에서 검증했다는 이유만으로 안전하다고 판단하지 않는다.

URL Parameter, Query Parameter, Request Body, Header, Cookie 등 백엔드에서 처리하는 외부 입력값은 사용 목적에 맞게 서버에서도 검증한다.

### ❌ Bad

```
value = request.parameter

중요로직(value)
```

### ✅ Good

```
value = request.parameter

if value가 해당 기능에서 허용하는 조건을 만족:
    중요로직(value)
else:
    요청 거부
```

입력값의 용도에 따라 필요한 형식, 범위, 길이 등을 검증한다.

## BE-02. 중요 업무 값 서버 검증

주문·결제 등에 사용되는 가격, 수량, 사용자 식별자, 업무 상태 등의 중요 값을 클라이언트 요청값만으로 결정하지 않는다.

### ❌ Bad

```
paymentAmount = request.price

결제(paymentAmount)
```

### ✅ Good

```
상품/주문 정보 = 서버 데이터 조회

paymentAmount = 서버 기준으로 검증 또는 계산

결제(paymentAmount)
```

# B. Injection · 데이터베이스

| 항목ID | 요구사항 | 조치 방법 | 근거 |
| --- | --- | --- | --- |
| BE-03 | 코드 인젝션 방지 | 사용자 입력값을 실행 가능한 명령·코드에 직접 결합하지 않음 | CI |
| BE-04 | SQL Injection 방지 | SQL 구조와 외부 입력값을 분리하여 처리 | SI |

## BE-03. 코드 인젝션 방지

외부 입력값을 운영체제 명령어, 템플릿, XPath 등 실행 가능한 명령 또는 코드의 일부로 직접 사용하지 않는다.

### ❌ Bad

```
command = "실행명령 " + userInput

execute(command)
```

### ✅ Good

```
if userInput이 서버에서 허용한 값:
    사전에 정의된 기능 실행
else:
    요청 거부
```

가능한 경우 사용자가 명령 자체를 구성하지 못하도록 하고 서버에서 정의한 값만 사용하도록 한다.

## BE-04. SQL Injection 방지

현재 프로젝트에서는 MySQL과 PostgreSQL을 사용하므로 데이터베이스 조회·등록·수정·삭제 코드에 적용한다.

사용자 입력값을 SQL 문자열에 직접 결합하지 않는다.

### ❌ Bad

```
sql =
    "SELECT * FROM member WHERE member_id = '"
    + memberId +
    "'"
```

### ✅ Good

```
sql = "SELECT * FROM member WHERE member_id = ?"

execute(sql, memberId)
```

Prepared Statement 또는 실제 프로젝트에서 사용하는 DB 접근 기술의 **파라미터 바인딩 기능**을 사용하여 SQL 구조와 입력값을 분리한다.

### 확인사항

- 사용자 입력값을 SQL 문자열에 직접 결합하지 않는가?
- SQL과 입력값이 분리되어 처리되는가?
- SQL문이나 DB 상세 오류가 API 응답에 노출되지 않는가?

# C. 인증 · 권한 · 세션

| 항목ID | 요구사항 | 조치 방법 | 근거 |
| --- | --- | --- | --- |
| BE-05 | 인증 절차 검증 | 보호된 기능 실행 전 서버에서 사용자 인증 상태 검증 | IA |
| BE-06 | 사용자·관리자 권한 검증 | 데이터 및 기능 접근 권한을 서버에서 검증 | IN, AE |
| BE-07 | 비밀번호 정책 | 비밀번호 정책을 서버에서도 검증 | BF |
| BE-08 | 비밀번호 복구 보호 | 예측하기 쉬운 복구 방식 및 임시 비밀번호 사용 방지 | PR |
| BE-09 | CSRF 방지 | 적용 대상 요청에서 위조 요청을 검증·차단 | CF |

## BE-05. 인증 절차 검증

인증이 필요한 API와 기능은 서버에서 사용자의 인증 상태를 확인한다.

### ❌ Bad

```
if request.login == true:
    보호 기능 실행
```

### ✅ Good

```
currentUser = 서버 인증정보 확인

if currentUser가 정상적으로 인증됨:
    보호 기능 실행
else:
    요청 거부
```

URL 직접 접근이나 요청값 변경으로 인증 절차를 우회할 수 없도록 한다.

## BE-06. 사용자 · 관리자 권한 검증

로그인 여부와 특정 데이터 또는 기능에 접근할 수 있는 권한은 구분하여 검증한다.

### ❌ Bad

```
GET /orders/{orderId}

order = findOrder(orderId)

return order
```

### ✅ Good

```
currentUser = 서버 인증 사용자
order = findOrder(orderId)

if currentUser가 해당 주문에 접근할 권한 보유:
    return order
else:
    접근 거부
```

관리자 기능 역시 URL 경로만으로 보호되는 것으로 판단하지 않고 서버에서 관리자 권한을 확인한다.

### 확인사항

- 다른 사용자의 리소스 식별자를 변경하여 데이터에 접근할 수 없는가?
- 조회뿐 아니라 수정·삭제에서도 권한을 확인하는가?
- 관리자 기능에서 관리자 권한을 별도로 확인하는가?

## BE-07. 비밀번호 정책

비밀번호 설정 기능이 있는 경우 프론트엔드 검증에만 의존하지 않고 서버에서도 서비스의 비밀번호 정책을 검증한다.

구체적인 비밀번호 정책은 프로젝트에서 정한 계정 정책을 적용한다.

## BE-08. 비밀번호 복구 보호

사용자 ID나 쉽게 확인할 수 있는 정보를 이용하여 예측 가능한 임시 비밀번호 또는 재설정 값을 생성하지 않는다.

### ❌ Bad

```
temporaryPassword = userId + "1234"
```

### ✅ Good

```
사용자 본인 확인

→ 예측하기 어려운 재설정 값 생성
→ 등록된 이메일/SMS 등 확인된 경로로 전달
→ 비밀번호 재설정
```

## BE-09. CSRF 방지

브라우저가 인증정보를 자동으로 전송하는 방식 등을 사용하는 경우 중요한 상태 변경 요청이 정상적인 요청인지 검증한다.

KISA 가이드에서는 주요 변경 요청에 대한 CSRF Token 검증과 Referer/Origin 검증, SameSite 쿠키 등의 대응 방법을 제시한다.

```
인증 상태 확인
위조 요청 방어값 검증

if 검증 성공:
    상태 변경 처리
else:
    요청 거부
```

구체적인 적용 방식은 실제 인증 구조에 맞게 선택한다.

## BE-10. 세션 · 인증 토큰 · 쿠키 관리

세션을 사용하는 경우 추측 가능한 세션 ID 또는 고정된 세션 ID를 사용하지 않고 만료 정책을 적용한다.
JWT 등 인증 토큰을 사용하는 경우 서명 등 토큰의 유효성과 만료 여부를 서버에서 검증한 후 인증정보로 사용한다.

### ❌ Bad

```
token 내용을 단순히 읽음

role = token.role

권한 허용
```

### ✅ Good

```
token 서명 등 유효성 및 만료 여부 검증

if 검증 성공:
    인증정보 사용
else:
    요청 거부
```

또한 사용자의 권한과 같은 중요한 상태를 클라이언트가 변경할 수 있는 쿠키 값만으로 결정하지 않는다.

## BE-11. 프로세스 우회 방지

주문·결제 등 여러 단계로 이루어진 업무에서는 클라이언트 요청만으로 다음 단계가 실행되지 않도록 현재 업무 상태를 서버에서 확인한다.

### ❌ Bad

```
/step1
/step2
/complete

/complete 요청이 들어오면 바로 완료 처리
```

### ✅ Good

```
currentState = 서버 데이터에서 현재 상태 확인

if currentState가 다음 단계 수행 가능한 상태:
    요청 처리
else:
    요청 거부
```

### 확인사항

- 필요한 중간 단계를 임의로 생략할 수 없는가?
- 이미 완료·취소된 업무가 비정상적으로 다시 처리되지 않는가?
- 가격, 수량, 업무 상태 등 중요 값을 서버에서 확인하는가?

## BE-12. 자동화 공격 방지

로그인, 본인확인, 인증번호 검증 등 반복 호출을 통해 공격에 악용될 수 있는 기능에는 필요한 반복 요청 통제를 적용한다.

구체적인 허용 횟수와 차단 시간은 서비스 정책에 따라 결정한다.

## BE-13. XSS 대응

백엔드에서 직접 HTML을 생성하거나 사용자 입력값을 HTML 콘텐츠로 반환하는 경우 해당 값이 스크립트로 실행되지 않도록 적절하게 처리한다.

단순 JSON API를 반환하고 실제 HTML 렌더링을 프론트엔드가 수행하는 경우 프론트엔드 시큐어 코딩 가이드의 XSS 기준을 적용한다.

## BE-14. 파일 업로드 검증

허용된 파일 형식만 서버에서 검증하여 업로드하고, 업로드된 파일이 서버에서 실행되지 않도록 한다.

```
파일명 검증
허용된 확장자 및 파일 유형(MIME 등) 검증

if 허용된 파일:
    지정된 위치에 저장
else:
    업로드 거부
```

## BE-15. 파일 다운로드 검증

사용자가 전달한 경로를 서버의 실제 파일 경로로 그대로 사용하지 않는다.

```
requestedFile = 요청값 검증
actualPath = 경로 정규화

if actualPath가 허용된 다운로드 영역 내부:
    파일 제공
else:
    요청 거부
```

`../` 등의 입력으로 허용되지 않은 디렉터리나 시스템 파일에 접근할 수 없도록 한다.

## BE-16. SSRF 방지

사용자 입력값에 따라 백엔드 서버가 URL 요청을 수행하는 기능이 존재하는 경우 요청 가능한 대상을 검증하고 제한한다.

### ❌ Bad

```
url = request.url

httpRequest(url)
```

### ✅ Good

```
url = request.url

if url이 서버에서 허용한 요청 대상:
    요청 수행
else:
    요청 거부
```

## BE-19. 필요한 HTTP Method만 사용

각 API는 실제 기능에 필요한 HTTP Method만 명확하게 사용한다.

특정 Method가 존재한다는 사실만으로 취약한 것은 아니며, 실제 서비스에 불필요하거나 악용 가능한 Method가 허용되는지를 확인한다.

## BE-20. CORS 설정

프론트엔드 시큐어 코딩 가이드에서는 **CORS 설정 자체를 백엔드 API 영역**으로 구분하고 있다. 또한 백엔드 API의 허용 Origin을 확인하고 Origin 값을 검증 없이 그대로 반사하지 않도록 명시하고 있다.

허용할 Origin을 명시적으로 제한하고 요청의 Origin 값을 검증 없이 그대로 허용하지 않는다.

### ❌ Bad

```
Access-Control-Allow-Origin =
    요청의 Origin 값을 검증 없이 그대로 사용
```

### ✅ Good

```
if 요청 Origin이 서버에서 허용한 Origin 목록에 포함:
    해당 Origin 허용
else:
    허용하지 않음
```

인증정보를 포함한 요청이 필요한 경우 프론트엔드의 요청 방식과 백엔드 CORS 설정을 함께 확인한다.

# I. 프론트엔드 연계 사항

다음 항목은 프론트엔드와 백엔드가 역할을 구분하여 함께 적용한다.

- 클라이언트 입력 검증은 보조 수단이며, 실제 중요 입력값은 서버에서도 검증
- 사용자 및 관리자 권한은 서버에서 최종 검증
- 실제 인증 구조에 따라 필요한 CSRF 방어 적용
- 파일 업로드 기능 사용 시 서버에서 파일 재검증
- CORS 설정은 프론트엔드의 실제 Origin 및 요청 방식과 맞춰 구성

프론트엔드 가이드에는 **클라이언트의 Role 분기는 UX용이며 실제 권한 검증은 서버에서 재확인하고, 클라이언트 입력 검증 역시 보조 수단으로 두고 서버에서 별도 검증해야 한다고 명시되어 있다.**

또한 CORS의 실제 설정은 백엔드 API 영역이며, 프론트엔드에서는 해당 설정을 확인하는 역할로 구분되어 있다.
