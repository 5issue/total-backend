# 0. 이 문서를 읽기 전에 알아야 할 것

**auth-service는 토큰·세션 관리자이고, 인증을 수행하는 주체는 각 서비스다.**

```
[클라이언트] ──① 로그인──────────────▶ [auth-service]  토큰 발급·회전·폐기
             ◀─ access token ────────

[클라이언트] ──② Bearer 토큰 첨부────▶ [order-service] ← 여기서 직접 검증한다
                                          │
                                          └─ 공개키만 필요 ──▶ auth-service의 JWKS
```

즉 order-service가 요청을 받으면 **auth-service에 물어보지 않고 스스로 서명을 검증**한다(설계서 3.4). `common`의 인증 처리기는 그 검증을 8개 서비스가 동일한 규칙으로 하도록 만든 공용 부품이다.

# 1. 적용 절차 (3단계)

## 1단계 — 모든 엔드포인트에 인가 애노테이션 표기

**이걸 먼저 해야 한다.** 2단계에서 기능을 켜면, 표기가 없는 핸들러가 하나라도 있을 때 **애플리케이션이 기동되지 않는다.**

| 애노테이션 | 의미 | 예 |
| --- | --- | --- |
| `@PublicApi` | 비로그인 접근 허용 | 상품 목록·상세, 공개 조회 |
| `@Authenticated` | 로그인만 필요, 역할 무관 | 장바구니 담기, 찜 토글 |
| `@RequireRole(Role.ADMIN)` | 특정 역할 필요 | 백오피스 기능 |

메서드 표기가 클래스 표기보다 우선한다. 컨트롤러 전체가 관리자용이면 클래스에 한 번만 붙여도 된다.

```java
@RestController
@RequestMapping("/api/v1/products")
@RequiredArgsConstructor
public class ProductController {

    @PublicApi                                  // 둘러보기는 비로그인 허용
    @GetMapping
    public ApiResponse<List<ProductResponse>> list() { ... }

    @PublicApi
    @GetMapping("/{id}")
    public ApiResponse<ProductResponse> detail(@PathVariable Long id) { ... }

    @RequireRole(Role.ADMIN)                    // 등록은 관리자만
    @PostMapping
    public ApiResponse<ProductResponse> create(@Valid @RequestBody ProductCreateRequest request) { ... }
}
```

> 설계서 2.5: 둘러보기·조회는 비로그인 공개, **개인화·구매 액션(장바구니·주문·결제·찜·작성)부터 인증** 필요.

## 2단계 — `application.yml` 설정

```yaml
kurly:
  security:
    enabled: true
    issuer: ${JWT_ISSUER:https://auth.kurly.local}
    audience: ${JWT_AUDIENCE:kurly-api}
    jwks-uri: ${JWT_JWKS_URI:http://localhost:8081/.well-known/jwks.json}
```

| 프로퍼티 | 필수 | 설명 |
| --- | --- | --- |
| `enabled` | ✅ | `true`일 때만 처리기가 동작한다. 기본 비활성 |
| `issuer` | ✅ | **전 서비스가 동일해야 한다.** 다르면 모든 토큰이 거부된다 |
| `audience` | ✅ | 〃 |
| `jwks-uri` | ✅ | auth-service의 JWKS 주소. **평문(http)은 로컬 호스트와 `*.svc.cluster.local`만 허용**하며 그 외에는 기동이 중단된다. 아래 환경별 값 참조 |
| `clock-skew` | | 시각 오차 허용치. 기본 `30s` |
| `fallback-jwk` | | JWKS 조회 실패 시 쓸 공개키(JWK JSON). 4-③ 참조 |
| `audit-packages` | | 기동 검사 대상 패키지. 기본 `com.kurly` |

### 환경별 값

| 변수 | local | prod |
| --- | --- | --- |
| `JWT_ISSUER` | `https://auth.kurly.local` | `https://auth.<팀도메인>` |
| `JWT_AUDIENCE` | `kurly-api` | `kurly-api` |
| `JWT_JWKS_URI` | `http://localhost:8081/.well-known/jwks.json` | `http://auth-service.kurly.svc.cluster.local/.well-known/jwks.json` |

**`issuer`는 라우팅 주소가 아니라 발급자의 안정적 식별자다.** 내부 DNS나 ALB 호스트명을 쓰면
인프라가 바뀔 때 발급된 토큰이 전부 무효가 된다. JWKS가 놓이는 퍼블릭 origin을 쓰고,
**끝에 슬래시를 붙이지 않는다** — 문자열 완전 일치라 `.../`와 `...`는 다른 값이다.

**`jwks-uri`는 반대로 실제로 조회할 주소다.** 운영은 ALB에서 TLS를 종료하고 내부 구간을
재암호화하지 않으므로(인증인가_설계서 0장·3.2) 클러스터 내부 평문 주소를 쓴다.
짧은 이름(`auth-service.kurly`)은 검색 도메인에 의존해 환경마다 다른 대상을 가리킬 수 있어
거부한다. **FQDN으로 적는다.**

**`issuer`·`audience`를 바꾸면 발급된 토큰이 전부 무효가 되고 전 서비스를 동시에 배포해야 한다.**
실사용자가 생기기 전에 확정한다.

`issuer`·`audience`가 auth-service와 한 글자라도 다르면 **모든 요청이 401**이 된다. 값 자체는 확정 대기 중이므로(검토요청서 A-2) 환경변수로 주입하고 하드코딩하지 않는다.

## 3단계 — 기동 확인

정상이면 이 로그가 찍힌다.

```
c.k.c.s.HandlerAuthorizationAuditor : 엔드포인트 인가 정책 검사 통과 (검사 패키지: com.kurly)
```

표기를 빠뜨렸다면 **포트가 열리기 전에** 기동이 중단되고, 어느 핸들러인지 알려준다.

```
IllegalStateException: 인가 정책이 지정되지 않은 엔드포인트가 있습니다.
@PublicApi, @Authenticated, @RequireRole 중 하나를 반드시 표기해야 합니다.
  - {GET [/api/v1/orders/{id}]} → OrderController#detail
```

# 2. 인증된 사용자 정보 사용하기

## 컨트롤러에서 받기

`@AuthPrincipal` 파라미터로 주입받는다.

```java
@Authenticated
@GetMapping("/{orderId}")
public ApiResponse<OrderResponse> detail(@PathVariable Long orderId,
                                         @AuthPrincipal AuthenticatedPrincipal me) {
    return ApiResponse.success(orderService.getById(orderId, me));
}
```

`AuthenticatedPrincipal`이 담고 있는 것은 **`userId`와 `role` 두 개뿐**이다. 토큰에 민감정보를 넣지 않는다는 설계서 1.3 원칙 때문이며, 그 외 회원 정보가 필요하면 해당 서비스에서 조회한다.

## 서비스 계층으로는 파라미터로 넘긴다

**`ThreadLocal`에 담아 어디서든 꺼내 쓰는 방식은 쓰지 않는다.** 톰캣이 스레드를 재사용하므로 정리를 한 번 빠뜨리면 **다음 요청이 이전 사용자의 신원을 물려받고**, 그 상태로 권한 검사를 통과한다. 조용히 잘못된 권한으로 동작하는 가장 나쁜 실패다.

파라미터로 넘기면 "이 메서드는 호출자 신원이 필요하다"가 시그니처에 드러나 소유권 검사를 빠뜨렸을 때 리뷰에서 보인다.

# 3. 소유권 검사는 각 서비스가 직접 한다

**처리기는 인증과 역할까지만 담당한다.** 진입부는 리소스의 소유자가 누구인지 모르기 때문이다(설계서 2.3).

> user는 **본인 소유 리소스만** 접근(배송지·계좌·주문 등). 역할이 2종뿐이라 "남의 주문을 못 본다"는 역할만으로 표현 불가 → 소유권 규칙이 실질적 핵심. — 설계서 2.1

`@Authenticated`만 붙이고 소유권 검사를 빠뜨리면 **주문 번호만 바꿔서 남의 주문을 조회할 수 있다**(BE-06 위반).

```java
@Transactional(readOnly = true)
public OrderResponse getById(Long orderId, AuthenticatedPrincipal me) {
    Order order = orderRepository.findById(orderId)
            .orElseThrow(EntityNotFoundException::new);

    // 토큰의 sub와 리소스 소유자를 비교한다 (설계서 2.2)
    if (!me.isAdmin() && !order.getUserId().equals(me.userId())) {
        throw new ForbiddenException();
    }
    return OrderResponse.from(order);
}
```

- `me.isAdmin()`으로 관리자는 소유권 검사를 면제할 수 있다(설계서 2.2에서 허용, 정책으로 명시할 것)
- **조회뿐 아니라 수정·삭제에서도 확인해야 한다**(BE-06 확인사항)

# 4. 알아둘 동작

## ① 실패 응답

| 상황 | 상태 | `error` |
| --- | --- | --- |
| 토큰 없음 / 형식 오류 / 서명·만료 실패 | **401** | `UNAUTHORIZED` |
| 인증됐으나 역할 부족 | **403** | `FORBIDDEN` |
| 인증됐으나 타인 리소스 (서비스 계층에서 던짐) | **403** | `FORBIDDEN` |

응답은 공통 `ApiResponse` 포맷 그대로다. 처리기가 던지는 예외는 `DispatcherServlet` 안에서 발생해 `common`의 `GlobalExceptionHandler`가 처리하기 때문이다.

```json
{"status":"ERROR","message":"인증이 필요합니다.","data":null,"error":"UNAUTHORIZED","timestamp":"..."}
```

**실패 사유를 세분화하지 않는다.** "토큰이 만료됨" 같은 구분은 공격자에게 정보를 준다(BE-17). 상세는 서버 로그(`DEBUG`)에만 남는다.

## ② 검증 대상에서 제외되는 요청

- CORS 프리플라이트(`OPTIONS`) — 자격증명을 싣지 않는다
- 컨트롤러 핸들러가 아닌 요청(정적 리소스 등)
- `/error`

## ③ auth-service 장애 대비 — `fallback-jwk`

JWKS 조회는 캐시되지만, **auth-service가 내려간 상태에서 내 서비스가 재시작되면 캐시가 비어 있어 모든 토큰 검증이 실패**한다. 이를 막으려면 현재 공개키를 설정에도 넣어둔다.

```yaml
kurly:
  security:
    fallback-jwk: ${JWT_FALLBACK_JWK:}   # auth-service의 /.well-known/jwks.json에서 keys[0]을 복사
```

정상 상황에서는 원격 조회 결과가 우선하므로 키 회전 반영이 늦어지지 않는다. 원격이 실패하거나 일치하는 키가 없을 때만 쓰인다.

원격 조회에는 재시도·캐싱·선갱신·장애 허용·요청 제한이 이미 적용되어 있다. 특히 요청 제한은 **존재하지 않는 `kid`를 담은 토큰을 연속 전송해 JWKS 재조회를 유발하는 증폭 공격**을 막는다.

# 5. 하지 말아야 할 것

| 하지 말 것 | 이유 |
| --- | --- |
| 애노테이션 없이 엔드포인트 추가 | 기동이 막힌다. 그게 의도다 — 공개/보호 결정을 강제한다 |
| 경로 패턴으로 공개 목록 관리 | `/api/v1/orders/**` 하나로 보호 대상까지 열린다. 판단 근거는 애노테이션 하나뿐이다 |
| `role` 클레임을 문자열로 직접 비교 | `Role` enum을 쓴다. 오타가 런타임까지 드러나지 않는다 |
| 주체를 `ThreadLocal`에 보관 | 2장 참조. 신원 누수 위험 |
| `@Authenticated`만 붙이고 소유권 검사 생략 | 3장 참조. 타인 리소스 접근이 열린다 |
| 토큰을 직접 파싱해서 쓰기 | 검증 규칙(알고리즘 화이트리스트·`token_type`)이 빠진다. `JwtVerifier`를 쓴다 |
| auth-service에 토큰 검증을 요청 | 매 요청이 auth-service를 거쳐 단일 장애점이 된다. 각 서비스가 직접 검증한다(설계서 3.4) |

# 6. 트러블슈팅

| 증상 | 원인 | 조치 |
| --- | --- | --- |
| 기동 실패 — "인가 정책이 지정되지 않은 엔드포인트" | 애노테이션 누락 | 메시지에 나온 핸들러에 표기 |
| 기동 실패 — "kurly.security.jwks-uri가 필요합니다" | `enabled=true`인데 `jwks-uri` 미설정 | 설정 추가 |
| 모든 요청이 401 | `issuer`/`audience`가 auth-service와 불일치 | 양쪽 값 대조 |
| 모든 요청이 401 (설정은 맞음) | JWKS 조회 실패 | `jwks-uri` 접근 가능 여부 확인, 로그의 "원격 JWKS 조회 실패" 확인 |
| 401이지만 토큰은 유효 | refresh token을 보냈다 | access token을 보내야 한다. `token_type=ACCESS`만 통과한다 |
| 403이 나옴 | 역할 부족 | `@RequireRole` 값 확인 |
| `@AuthPrincipal`이 401을 던짐 | `@PublicApi` 핸들러에서 주체를 요구했다 | `@Authenticated`로 바꾸거나 파라미터를 뺀다 |
| 처리기가 아예 동작 안 함 | `enabled` 미설정 | `kurly.security.enabled=true` |

# 7. 적용 체크리스트

- [ ] 모든 컨트롤러 메서드에 `@PublicApi` / `@Authenticated` / `@RequireRole` 중 하나 표기
- [ ] `kurly.security.enabled`·`issuer`·`audience`·`jwks-uri` 설정
- [ ] 기동 로그에서 "엔드포인트 인가 정책 검사 통과" 확인
- [ ] 개인 리소스 조회·수정·삭제에 소유권 검사 추가
- [ ] 공개 엔드포인트가 정말 비로그인 공개여도 되는지 재확인
- [ ] 401/403 응답이 `ApiResponse` 포맷으로 나오는지 확인
- [ ] (운영 전) `fallback-jwk` 설정 여부 결정

# 8. 참고 — auth-service 적용 예시

auth-service가 첫 적용 사례다. 코드를 참고할 때 아래를 보면 된다.

| 파일 | 내용 |
| --- | --- |
| `AuthController` | `@PublicApi` 표기 예시 (로그인·재발급) |
| `JwksController` | 공개키 배포 엔드포인트 |
| `LocalJwkSourceConfig` | **auth-service 전용.** 서명키를 직접 보유하므로 자기 JWKS를 HTTP로 조회하지 않고 로컬 키를 쓴다. 다른 서비스는 이 설정을 따라 하면 안 된다 |
| `application.yml` | `kurly.security` 설정 (단 `jwks-uri`는 없음) |

# 9. 미확정 사항

가이드대로 적용하되, 아래는 확정 시 문서를 갱신한다.

| 항목 | 상태 |
| --- | --- |
| `issuer` / `audience` 실제 값 | 미확정 (검토요청서 A-2). 환경변수로 주입할 것 |
| CORS 허용 Origin | 미설정 (BE-20). 프론트 도메인 확정 대기 |
| CSRF 대응 근거 문서화 | 미완 (BE-09) |
| 소유권 검사 공통화 방식 | 현재는 각 서비스가 직접 구현. 설계서 2.2는 공통화를 권고하나 방식은 백엔드 재량 |
