# 세션 활동 이벤트 — 통신 명세

유휴 세션 자동 차단(인증인가_설계서 1.6)을 위해 **각 서비스가 사용자 활동을 auth-service에 알리는**
비동기 경로의 규약. 작성 2026-09-23.

- **발행자**: `kurly.security.enabled=true`인 모든 서비스 (공통 인증 처리기)
- **소비자**: auth-service
- **판정 단위**: **사용자**(단말 아님) — 3-4 참조

---

# 1. 왜 필요한가

유휴 판정 기준은 `user_refresh_tokens.last_used_at` / `admin_refresh_tokens.last_used_at`이다.
그런데 사용자의 실제 활동은 order·payment 등 **다른 서비스에서 일어나고**, auth-service는
그 호출을 볼 수 없다. access token이 stateless JWT라 매 요청 저장소를 조회하지 않기 때문이다(1.5).

이 이벤트가 그 간극을 메운다.

```
last_used_at = max( 토큰 갱신 시 동기 기록,  활동 이벤트로 반영된 값 )
```

**동기 기록이 항상 먼저 있다.** 이벤트 경로가 통째로 죽어도 "마지막 갱신 시각" 기준으로 degrade할 뿐,
세션이 무더기로 끊기지 않는다. 이벤트는 갱신과 갱신 사이를 메우는 보강재다.

---

# 2. 토폴로지

| 구분 | 이름 |
| --- | --- |
| Exchange | `session.topic.exchange` (topic, durable) |
| Routing key | `session.user.activity` |
| Queue | `auth.user-activity.queue` |
| DLQ | **두지 않는다** (2-1 참조) |

> **명명 규약 예외**: 기존 컨벤션은 `{발행서비스}.topic.exchange`인데(`order.topic.exchange` 등),
> 이 이벤트는 **발행자가 전 서비스**라 소유 서비스가 없다. 그래서 도메인 이름(`session`)을 쓴다.
> 큐 이름은 컨벤션대로 소비자 기준(`auth.*`)을 따른다.

## 2-1. 큐 선언 인자 — 반드시 아래대로 고정한다

```java
QueueBuilder.durable(QUEUE_USER_ACTIVITY)
        .maxLength(100_000)                 // 상한
        .overflow(Overflow.dropHead)        // 넘치면 가장 오래된 것부터 버린다
        .ttl(120_000)                       // 2분 지난 이벤트는 자동 만료
        .build();
```

**DLX를 지정하지 않는다.** DLX가 있으면 RabbitMQ는 TTL로 만료된 메시지와 `drop-head`로
밀려난 메시지까지 dead-letter한다. 즉 **버리기로 한 메시지가 전부 DLQ에 쌓여** 상한 없는
적재처가 생기고, 결국 워터마크에 닿아 발행자가 블로킹된다 — 이 설계가 막으려던 그 상황이다.
형식이 어긋난 메시지는 리스너가 로그를 남기고 버린다(5-4).

**세 인자 모두 의도적이다.**

- **`drop-head`** — 소비자가 `userId`별 **최신 시각만** 남기므로 오래된 이벤트는 버려도 정보 손실이 없다.
  기본 동작(무제한 적재 → 브로커 워터마크 → **발행자 블로킹**)은 전 서비스의 인증 요청을 멈추게 하므로
  반드시 피해야 한다. **유실을 감수하는 쪽이 옳다.**
- **`ttl` 2분** — 유휴 한도(15~30분)보다 훨씬 짧다. 2분 지난 활동 기록은 지연 보정이 무시할 값이라
  쓸모가 없다. 적체가 구조적으로 2분어치를 넘지 못한다.
- **`maxLength`** — TTL이 못 막는 순간적 폭주의 상한.

> ⚠️ **이미 만들어진 큐의 인자는 나중에 바꿀 수 없다.** 인자가 다르면 선언이
> `PRECONDITION_FAILED - inequivalent arg`로 거부된다(2026-09-22 order-service 사례).
> dev·운영 배포 전에 확정한다.

# 3. 메시지

## 3-1. 스키마

```json
{
  "userId": 1001,
  "role": "USER",
  "occurredAt": "2026-09-23T12:34:56.789Z",
  "service": "order-service"
}
```

| 필드 | 타입 | 필수 | 설명 |
| --- | --- | --- | --- |
| `userId` | `Long` | ✅ | access token의 `sub`. 회원 도메인 참조값 |
| `role` | `String` | ✅ | `USER` / `ADMIN` — 갱신 대상 테이블을 가른다 |
| `occurredAt` | `Instant` | ✅ | 활동 발생 시각(UTC). **발행 시각이 아니라 요청 처리 시각** |
| `service` | `String` | ⚪ | 발행 서비스. 판정에 쓰지 않고 관측용 |

직렬화는 `common`의 `RabbitMqAutoConfiguration`이 제공하는 JSON `MessageConverter`를 쓴다
(Jackson 3 `tools.jackson`).

## 3-2. 순서·중복

**순서 보장이 필요 없고, 중복도 무해하다.** 소비자가 `max(occurredAt)`만 취하므로
늦게 도착한 과거 이벤트는 자연히 무시된다. 재전송·중복 발행에 별도 처리가 필요 없다.

## 3-3. 담지 않는 것

**토큰 원문·JWT·개인정보를 싣지 않는다**(설계서 3.5 — 비동기 이벤트에는 식별정보만).
세션/단말 식별자도 싣지 않는다(3-4 참조).

## 3-4. 판정 단위가 사용자인 이유와 그 한계

이벤트는 `userId`만 싣고, 소비자는 **그 사용자의 활성 토큰 행 전체**를 갱신한다.

단말 단위로 하려면 회전을 가로질러 유지되는 세션 식별자를 신설하고 access token에 `sid`
클레임을 추가해야 한다(전 서비스 재배포 필요, 2.5~3일). **1단계에서는 사용자 단위로 간다.**

> **알려진 한계**: 방치된 단말의 세션도 **다른 기기에서의 활동으로 함께 연장된다.**
> "자리 비움 단말 차단"이라는 제6조 취지를 온전히 충족하지 못한다. 보안팀 보고 대상이며,
> 단말 단위 전환은 별도 과제로 둔다.

# 4. 발행 (각 서비스)

## 4-1. 위치

`common`의 `AuthenticationInterceptor` — 토큰 검증 **성공 직후**.
검증 실패 요청은 활동이 아니므로 발행하지 않는다.

## 4-2. 디바운스 — 파드 로컬 메모리

```java
// (역할, userId) 키, 60초 TTL. 이미 최근에 보냈으면 건너뛴다.
// USER와 ADMIN은 서로 다른 테이블의 id라 값이 겹칠 수 있어 역할을 키에 포함한다.
String key = role + ":" + userId;
if (debounceCache.asMap().putIfAbsent(key, Boolean.TRUE) != null) return;
publish(event);
```

- **Redis를 쓰지 않는다.** 공유 저장소로 파드 간 중복까지 제거할 수 있지만, 그러려면
  **매 인증 요청마다 Redis 왕복**이 임계 경로에 들어간다. 얻는 것은 메시지 수 절감뿐이고,
  소비자가 어차피 병합하므로 **중복은 무해하다.**
- 파드가 N개면 사용자당 최대 N배 발행된다. 활성 1000명·파드 3개·60초 기준 **초당 약 50건**으로,
  RabbitMQ에 부담이 되지 않는다.

## 4-3. 발행 실패는 삼킨다

```java
publisher.execute(() -> {                     // 버퍼 제한 전용 실행기
    try {
        rabbitTemplate.convertAndSend(EXCHANGE, ROUTING_KEY, event);
    } catch (Exception e) {
        log.debug("활동 이벤트 발행 실패", e);
    }
});
```

**요청 스레드에서 발행하지 않는다.** `convertAndSend`는 컨슈머 처리를 기다리지 않지만,
브로커에 연결할 수 없으면 호출 스레드에서 재연결을 시도하며 connection timeout까지 멈추고,
브로커가 `connection.blocked` 상태면 발행 자체가 막힌다. `try/catch`는 예외만 삼킬 뿐
대기 시간을 줄이지 못한다. 그대로 두면 **브로커 장애가 전 서비스의 인증 지연**이 된다.

전용 실행기(스레드 2, 버퍼 1000)로 넘기고 **버퍼가 차면 이벤트를 버린다.**
publisher confirms는 켜지 않는다.

## 4-4. 발행하지 않는 서비스

`kurly.security.enabled`가 없는 **wms·scm은 인증 처리기 자체가 비활성**이라 이벤트를 보내지 않는다.
두 서비스만 사용하는 사용자는 활동이 기록되지 않아 유휴로 오판된다.
**유휴 차단을 켜기 전에 두 서비스에 인증 처리기를 적용해야 한다.**

# 5. 소비 (auth-service)

## 5-1. 병합 후 배치 반영

```
수신 → userId별 max(occurredAt) 병합 → 5초마다 flush → 배치 UPDATE
```

```sql
UPDATE user_refresh_tokens t
  JOIN auth_users u ON u.id = t.auth_user_id
   SET t.last_used_at = :occurredAt
 WHERE u.user_id = :userId          -- 이벤트의 userId = access token sub = 회원 도메인 참조값
   AND t.is_revoked = false
   AND t.expires_at > :now
   AND (t.last_used_at IS NULL OR t.last_used_at < :occurredAt)
```

> ⚠️ **`auth_users.id`가 아니라 `auth_users.user_id`로 거른다.** 이벤트가 싣는 `userId`는
> access token의 `sub`이며 **회원 도메인 참조값**이다. `auth_users.id`(인증 도메인 PK)와
> 혼동하면 **다른 사용자의 세션을 갱신**한다. 관리자는 `auth_admins.admin_id`가 같은 역할이다.
>
> 비교 기준 시각(`:now`)도 DB의 `NOW()`가 아니라 애플리케이션에서 바인딩한다. 저장된 값이
> JDBC 드라이버를 거쳐 변환되므로, DB 함수와 섞으면 시간대가 어긋난다.

- **활성 행만** 갱신한다. 폐기·만료된 세션을 되살리지 않는다.
- **`last_used_at < :occurredAt` 조건**으로 과거 이벤트가 최신 기록을 덮어쓰지 못하게 한다.
- `role`에 따라 `admin_refresh_tokens`를 같은 형태로 갱신한다.

## 5-2. 반영 지연 관측

flush할 때마다 그 배치의 최신 활동 시각을 기록한다.

```java
processedUpTo = max(batch, e -> e.occurredAt());
지연 = now - processedUpTo
```

`지연`만으로는 *"한가해서 이벤트가 없음"* 과 *"밀려서 오래된 것만 처리 중"* 을 구분할 수 없다.
**큐 적체(`messages_ready`)와 함께 본다.**

**관측 자체가 낡으면 지연을 주장하지 않는다.** flush가 완료되지 못하면(예: DB 잠금) snapshot이
갱신되지 않는데, 그 값을 계속 믿으면 지연이 무한히 커져 **유휴 판정이 영구히 우회**된다.
법적 근거가 있는 통제가 조용히 꺼지는 상태이므로, 마지막 관측이 `auth.idle-timeout.lag-stale-after`
(기본 60초)보다 오래되면 지연을 0으로 보고 엄격 판정으로 돌아간다.

| 지연 | 적체 | 해석 |
| --- | --- | --- |
| 큼 | 없음 | 정상 (트래픽 없음) |
| 큼 | 있음 | **밀리는 중 — 판정 신뢰 불가** |

## 5-3. 지연 보정과 fail-open

판정 시 알고 있는 지연만큼 빼준다. 통제를 끄는 게 아니라 **사용자에게 유리하게 해석**한다.

```java
Duration lag = 적체중 ? Duration.between(processedUpTo, now) : Duration.ZERO;
Duration 체감유휴 = Duration.between(lastActivityAt, now).minus(lag);

if (lag.compareTo(유휴한도) >= 0) {
    log.error("유휴 판정 우회: lag={}, userId={}", lag, userId);  // 통제 해제 — 경보 대상
    return;                                    // 세션 유지
}
if (체감유휴.compareTo(유휴한도) > 0) {
    revokeAllSessions(userId);
    throw new UnauthorizedException();
}
```

## 5-4. 독성 메시지

리스너가 형식을 검사해 **로그를 남기고 버린다.** 재큐하면 잘못된 메시지 하나가 전체 소비를 막는다.

# 6. 운영 지표와 경보

| 지표 | 임계 | 의미 |
| --- | --- | --- |
| 반영 지연 | > 2분 **AND** 적체 > 0 | 컨슈머 장애로 취급 |
| fail-open 발동 | 1회라도 | **법적 근거 있는 보안 통제가 해제된 상태**. 즉시 경보 |
| 형식 오류 이벤트 로그 | 지속 발생 | 스키마 불일치·버그 |
| 큐 drop 수 | 지속 증가 | 발행량 과다 — 디바운스 주기 재검토 |

**fail-open은 감사 기록이 필요하다.** 우회한 시각·지속 시간·영향받은 갱신 건수를 남겨,
사후에 "언제 통제가 꺼져 있었는지" 답할 수 있어야 한다(1.7 접속기록과 함께).

# 7. 장애 시나리오

| 상황 | 동작 |
| --- | --- |
| 브로커 다운 | 발행 실패를 삼킨다 → 인증 정상. 판정은 **갱신 시 동기 기록 기준**으로 degrade |
| 컨슈머 지연 | 지연 보정이 흡수. 한도만큼 밀리면 fail-open |
| 큐 폭주 | TTL 2분 + `drop-head`로 자동 정리. 오래된 이벤트만 사라져 무해 |
| auth 재기동 | 큐에 쌓인 것을 이어서 소비. 미반영분은 TTL 내에서 복구 |
| wms·scm 사용자 | **활동 미기록 → 유휴 오판.** 인증 처리기 적용 전까지 남는 구멍 |

# 8. 적용 순서

1. ✅ auth-service — `last_used_at` 컬럼, 판정 로직, 갱신 시 동기 기록 (**완료**)
2. 이 명세 확정
3. `common` — 인터셉터 디바운스·발행, 큐/익스체인지 선언
4. auth-service — 컨슈머·병합·지연 관측
5. wms·scm에 인증 처리기 적용
6. **`auth.idle-timeout.enabled=true`로 전환** — 3~5가 끝난 뒤

> 3단계 전에 6을 켜면 "마지막 갱신 시각"만으로 판정하게 되어, access TTL(30분)이
> 유휴 한도(30분)보다 짧지 않아 **활동 중인 사용자가 상시 차단된다.**

# 9. 배포 시 주의

## 9-1. 배포 순서 — auth(소비자)를 먼저

발행자가 먼저 뜨면 익스체인지는 생기지만 바인딩된 큐가 없어 **메시지가 버려진다.**
장애는 아니지만 그 기간의 활동 기록이 비어, 켤 때 판정 근거가 부족해진다.

## 9-2. 큐 인자는 생성 후 바꿀 수 없다

`max-length`·`overflow`·`ttl`이 한 곳이라도 다르면 선언이
`PRECONDITION_FAILED - inequivalent arg`로 거부된다. 바꾸려면 큐를 지우고 다시 만들어야 한다.

## 9-3. Flyway 이력이 없는 기존 DB는 version 0으로 baseline

`baseline-on-migrate`는 **`false`로 둔다.** `true`로 바꾸면 기본 baseline version이 `1`이라
**`V1__add_last_used_at.sql`을 이미 적용된 것으로 간주하고 건너뛴다.** 그러면 컬럼이 생기지 않는다.

Flyway 이력 없이 운영 중인 DB가 있다면 배포 전에 **version `0`으로 일회성 baseline** 처리한다.

```bash
flyway baseline -baselineVersion=0 -baselineDescription="init auth"
```

## 9-4. 켜는 순서

`auth.idle-timeout.enabled=true`는 **활동 기록이 충분히 쌓인 뒤** 켠다. 배포 직후에는 기존
세션의 `last_used_at`이 비어 있어 `created_at`(최대 14일 전)으로 판정되므로, 바로 켜면
활동 중이던 사용자까지 끊긴다. 발행·소비는 `enabled=false`에서도 동작하므로 그 기간이
곧 워밍업이 된다.
